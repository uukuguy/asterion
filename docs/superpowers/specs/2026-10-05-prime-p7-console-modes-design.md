# P7 控制台三模式整体设计

日期：2026-10-05。状态：设计提案，待用户审阅。回放已实现；实时人工、实时 P7 和接管尚未实现。

## 目标与范围

控制台管理本地可用的 ARC-AGI-3 题目和关卡。主画面显示游戏。右侧显示当前游戏认识。过程区显示 P7 的目标、决策摘要、动作和反馈。P7 的任务是过关。假说用于补足认识，不能成为要求逐条验证的任务清单。

同一个界面提供回放、P7 过关、人工游戏三种模式。同一个真实游戏会话可在 P7 与人工之间交接。浏览器不持有游戏引擎，也不直接调用模型。

沿用单个自包含 HTML、内嵌 Tailwind CSS 和原生 JS。离线文件可独立打开。实时操作需要本地 Python 服务；前端仍无需构建步骤或 CDN。先支持一个活动游戏会话，不在本次设计中增加并行游戏调度和官方提交功能。

## 方案选择

| 方案 | 收益 | 代价 |
| --- | --- | --- |
| 共用界面、本地 Python 游戏会话（推荐） | 复用引擎、broker 和记录；人工与 P7 可接同一局 | 需要分离游戏与求解任务生命周期 |
| 三个独立控制台 | 各模式容易独立开发 | 状态、展示和接管接口重复；过程容易断开 |
| 浏览器内运行游戏和求解 | 浏览器可直接响应操作 | 重复现有执行链；改变打包、权限和部署边界 |

## 模式与操作

| 模式 | 主画面 | 动作键 | 主要控制 |
| --- | --- | --- | --- |
| 回放 | 选中记录的真实帧 | 定位同名已录动作，不执行新动作 | 播放、暂停、时间轴、前后动作 |
| P7 过关 | 当前真实游戏帧 | 高亮 P7 当前动作；禁止人工发动作 | 启动 P7、暂停、人工接管、结束 |
| 人工游戏 | 当前真实游戏帧 | 执行一个可用动作 | 动作键、坐标点击、交给 P7、结束 |

动作区只放按键、短含义和小状态标记。例如 `ACTION4 · 右移 · 已识别`，或 `ACTION3 · 左移 · 推测`。完整依据放在认识与过程区。动作含义只来自已保存的认识或明确标记的推断，不按编号预置方向。当前执行动作高亮。

回放中的动作含义若来自最终认识，注明“最终动作认识”。实时模式显示与当前观察关联的认识版本。不能把最终认识当作历史时点已经获得的认识。

人工操作采用本帧的 `available_actions`。坐标动作只在其可用时启用，点击画布后显示坐标并发送单次动作。键盘控制只有在游戏区获得焦点时启用；禁止按住键重复发送和忙碌时排队旧动作。RESET 只在会话允许时出现，并明确显示“重试当前关卡”。

默认只显示真实游戏画面。变化格、动作位置、前后对照作为可选回放覆盖层，默认关闭。颜色采用名称加编号。不能把画面颜色或位置直接解释为目标、分数或进度。

顶部持续显示：模式、题目、关卡、游戏状态、控制方、连接状态。P7 暂停、等待动作结算、人工控制、历史回放要有不同文字状态，不能只靠颜色区分。

## 题目与关卡管理

题目列表读取本地游戏目录的公开元数据：题目 ID、别名、关卡数量和可用记录。启动时显示最近记录；没有记录时显示题目列表，不要求用户填写长路径。

关卡完成只依据游戏权威的 `levels_completed` 或 WIN。列表区分“已过关”“进行中”“未开始”“没有记录”。未观察到的关卡不生成假画面。历史记录与当前局分开，人工、纯 P7 和混合控制的结果各自标明。

一次只运行一个局。切换到其他真实题目前，明确结束当前局。查看历史不创建新游戏。恢复历史帧不等于恢复引擎；如以后支持重放动作前缀来重建状态，必须创建新会话并逐步核对结果。

## 会话、控制权与生命周期

Python 应用层持有 `GameSession`：引擎、broker、观察、动作历史、认识版本和记录。P7 求解是附着于该会话的 `SolverSegment`。人工动作也经过 broker。所有游戏动作串行执行。

会话记录 `session_id`、`episode_id`、控制方 `human/p7/none`、`control_epoch`、观察版本和连续事件序号。每次改变控制权增加 epoch。动作、RESET 和依赖观察的计划必须带当前观察版本。暂停、结束和接管请求只要求有效控制者、session 与 epoch，不能因 P7 正在刷新观察而无法暂停。

写命令带命令 ID。先查去重记录，再检查版本。同 ID、同内容返回原结果，不重复执行；同 ID、不同内容被拒绝。新命令的旧标签页、旧计划和旧观察被拒绝。模型读取和合法游戏动作不靠认识中的“已确认”标签获得权限。

P7 暂停或人工接管按以下顺序执行：

1. 进入“等待结算”，停止接受新的 P7 游戏动作调用。
2. 等待已经开始的调用结束。第一阶段以整个调用为边界；多步调用可能需要等待多步。界面显示等待状态，不宣称已经暂停。
3. 确认没有执行中的动作，停止或静止该求解段，关闭未完成实验并使旧动作计划失效，保留引擎与 broker。人工动作不能进入 P7 的旧实验。
4. 增加 epoch，发送新观察，交给人工或进入暂停状态。
5. 再启动 P7 时，新求解段接收最新画面、完整相关动作历史和认识，不允许继续使用旧预期。

交接保留游戏状态，不承诺保留 Pi 内部会话或未公开的模型思考。人工动作进入真实历史；再次交给 P7 时作为反馈提供。模型可分析它们，但不能伪造这些动作曾由 P7 预先选择或登记为实验。

从实时模式进入历史回放，默认先暂停并等待结算，然后显示历史。回放期间会话保持暂停。返回实时视图获取最新观察；由用户选择继续人工或启动 P7。离线回放不存在活动游戏会话。

P7 的阶段目标达到后结束求解段，并保留本局供查看或人工继续。broker 使用整局目标和固定动作上限；求解段有独立阶段目标与完成事件，不调用 `broker.seal()`。应用级阶段完成适配与现有终局收据分开，原独立 level-witness 入口保持其收据语义。预算耗尽后会话不能再执行动作；不能重建 broker 来续预算。

游戏最终 WIN、不可恢复故障或用户结束会关闭会话。可 RESET 的 GAME_OVER 进入“需要重试”，保留本局。RESET 后增加 `episode_id`，保留 session、已完成关卡和单调递增的动作与事件序号。模型轮次用 `solver_segment_id + round_index`，不与关卡重试混淆。当前 broker 达到 target_level 会关闭，operator 又在求解结束时关闭引擎；这些生命周期必须拆开，不能只改 UI 标签实现继续玩。

## P7 过程与游戏认识

过程采用明确的关联链：`观察版本 → P7 决策摘要 → 动作 → 结算观察 → 认识更新`。每条记录带题目、轮次、关卡、控制方和动作序号。P7 摘要包含目标、简短依据、选中动作和预期反馈。它由 P7 显式输出，不从工具调用倒推，也不要求展示私有思维链。

一个决策可对应多个动作。每步都有真实前后帧、结算结果和关卡进度。界面可展开该批动作。动作后显示对象位移、游戏状态变化、P7 的反馈解释和认识修改；没有 P7 解释时明确标记缺失。像素测量与 P7 得出的结论分开。

稳定游戏认识是一份逐步完善的玩法介绍：游戏类型、物件、控制、规则、过关条件。确定事实、规划推断和未知项明确区分。描述使用短句、固定术语、明确主体与条件，采用适用于中文的简化技术写作原则；不宣称通过英语 ASD-STE100 的认证或未经评估的百分比。

假说针对介绍中的缺口和过关阻碍。可以依靠游戏常识作高置信推断并先用于规划，在正常动作中顺便检验。一个动作可以支持或否定多个相关假说。策略与假说分别记录。分数、进度、计时、资源和状态显示由 P7 观察与反馈识别；提示只提醒关注这些部件，不填入本题答案。

每次认识更新带 `cognition_revision` 及证据观察、动作关联。主要认识区随时间轴选择对应版本。仅有最终认识的旧记录保留现有范围提示，不补造历史版本。默认显示完整玩法介绍及本轮差异，全部假说依据可展开查看。

## 应用接口与部署

新增会话和服务代码只放在 `src/asterion/applications/prime/p7/`。复用 `ArcadeEngine`、`ArcBroker`、P7 client 和现有打包的页面资源。通用 runtime、runner 和闭合协议不增加游戏专用逻辑。

本地浏览器接口仅提供固定操作：题目列表、创建/结束会话、读取快照、订阅事件、人工动作、启动 P7、暂停/接管。浏览器不能指定命令、文件路径、provider、model 或无限预算。启动 P7 使用已有 operator 配置与有限预设；打开控制台本身不调用模型。

实时服务绑定 loopback，页面与 API 同源。写请求校验服务生成的会话令牌、Origin 和会话版本。离线 HTML 保持 `connect-src 'none'`；实时页面只允许连接本地同源接口。公开事件不含密钥、私有路径、provider 原始载荷或未公开模型输出。

现有真实运行由 Mac 调用 Orb guest。guest 的 loopback 不等于 Mac loopback。游戏、broker 和 P7 放在同一执行侧；Mac 服务通过固定、受控的 Orb 通道转发请求与事件。页面不能直接访问内部 `P7ClientServer` 或 IPython bridge。该跨主机通道需要单独验证，不能假定现有内部 RPC 已是浏览器服务。

事件使用应用专用、可重放的安全投影，带序号和上述关联 ID。先用顺序事件订阅和有限缓冲支持断线恢复；缺口超过保留范围时重新获取快照。持续保存帧、动作、决策摘要、认识版本和控制权变化。结束时可导出一个离线 HTML。

完成后日常入口仍为 `make p7-console`：启动本地服务并打开界面，选择题目和模式。`make asterion-prime-p7-console` 保留只导出功能。离线文件保留播放器，不伪装实时操作可用。

## 异常与证据

活动控制标签页通过 heartbeat 保持有限租约；旁观页和事件流重连不授予控制权。guest 在控制租约过期或 Mac↔Orb 通道失效时关闭新动作入口，等待在途调用结算，然后暂停。重连不自动继续 P7。只有 guest 会话服务仍存活时才承诺保留游戏；进程退出按中断处理。

浏览器断线不重发游戏动作。人工命令以 ID 查询结算结果；租约失效后的控制命令须重新获得控制权。游戏保留到用户结束或服务退出。切换控制权需要显式完成上述交接。

引擎调用异常且无法确认动作是否生效时，锁定会话并显示“游戏状态不确定”。不自动重试动作。服务退出负责关闭引擎和求解进程并写入中断记录。

人工和 P7 共同推进的一局标为混合控制，不能算纯 P7 过关。收据保留所有实际动作的来源和数量。纯 P7、人工与混合会话的结果分别统计。达到阶段目标、正常未完成、引擎故障也分别显示，不能一律写成过关或模糊失败。

现有 broker 的无变化保护也会影响人工操作。首个人工版本保留并明确显示限制；若要改变，先审查应用级策略并验证，不能让人工入口绕过 broker。

## 实施顺序与验收

整体设计分成四个可独立验收的实现包，按顺序开展。各包再制定具体实现计划。

1. **人工实时会话**：共用界面，接本地服务、题目选择、单次动作、重置、结束和事件流。动作不调用模型；验证真实前后帧、可用动作、重复命令及断线结果查询。保留原离线导出。
2. **P7 附着会话**：拆分游戏与求解段生命周期，接启动、调用边界暂停和关联事件。显示明确 P7 决策摘要与真实动作反馈。阶段目标结束后游戏仍存在。
3. **同局接管**：接 P7→人工→P7，验证没有重启引擎、没有双重执行、旧计划失效、人工历史可读、结果来源正确。
4. **打包部署闭环**：验证 Mac/Orb 连接与断线、wheel 中页面资源、真实人工动作和有限 P7 level-witness。执行相关 Python/DOM 测试、lint、docs-check、promotion-check。扩展注册若改变，另执行 TypeScript 扩展测试。未通过的检查如实保留，真实过关结果单独报告。

关键验收不是按钮存在，而是同一局能从人工交给 P7，再暂停接回；画面、动作和认识的时间关系可查。成功导出、合成测试和页面交互通过都不能代替真实 P7 过关证据。

## 当前代码接点与未实现边界

- `console_export.py`、`console_snapshot.py`、`console_assets/`：离线导出与共享展示。
- `game.py`：本地题目选择和元数据。
- `live.py` 的 `ArcadeEngine`：真实引擎；内部 RPC 不作为公开浏览器接口。
- `broker.py` 的 `ArcBroker.act`：人工动作的受控入口；checked plan 继续用于 P7。
- `operator.py` 的 `run_live`：目前创建并最终关闭整局，必须分离生命周期。现有取消不能当作可恢复暂停。
- `runtime_binding.py`：现有运行收据流不等于完整游戏过程。应用事件投影另行实现，不改闭合通用协议。

本提案没有实现实时服务、会话复用或 P7 接管，也没有证明当前认识能够完成 SP80。现有回放仍是只读历史证据。
