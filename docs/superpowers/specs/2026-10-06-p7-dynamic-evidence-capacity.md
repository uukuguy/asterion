# P7 动态证据区与明确错误处理

2026-10-06。用户确定方向：长动画完整保存，采用独立动态容量区，不加入通用总长限制；专门处理，必要时持久化，使用后释放。越限与底层失败必须明确告警。本文是应用级设计；实现与部署状态以活动检查点为准。

## 已验证的问题

| 关卡 | 最近两次失败的直接证据 | 边界 |
| --- | --- | --- |
| BP35 L6 | SDK 已返回 GAME_OVER、57 帧；约569.8KB观察在完整 digest 计算时触发512KiB投影上限。随后分别92/93个事件中没有新动作。 | 两次确实死亡；本地把死亡结果错标未知，阻止 RESET。不能由此证明已有策略能通关。 |
| G50T L3 | SDK 已返回 NOT_FINISHED、95帧、389120 cells；完整 digest 触发262144 cells上限。两次33个新动作及前后digest完全相同，随后停止真实行动。 | 第二次读取并复用经验，但同点触发本地错误。SDK末结果仍只有2关，未证明第三关路线正确。 |
| LF52 L8 | 两次末观察3/2帧，snapshot/digest均通过；17/26个新动作、剩余92/83动作额度；多个合法登载预测失配。 | 属于交互模型未补全；未执行的prefix-action-reuse拒绝不能作为游戏反例。 |

只读复现使用既存SDK录制和纯观察函数，SDK重放、模型、官方调用均为0。私有证据：`launches/blocked-bp35-l6-readonly-analysis.json`、`launches/blocked-g50t-lf52-readonly-analysis.json`，相对于既有 operator root 的 live runs 目录。

核心问题有三处：完整动画与稳定状态共用小消息上限；模型截取末帧发生在全量校验之后；SDK返回后的本地异常被宽catch归为结果未知。网页另外有64动画帧限制，单修digest仍会丢展示记录。

## 选择

采用 **动态证据区＋旧规范哈希的流式计算＋稳定状态视图**。动画不进入通用小JSON容量预算。完整动画顺序和原观察身份保留，工具与网页按页引用。

比较过的替代方案：扩大固定总限额只能推迟同类错误，无法处理生命周期；改成新的末帧/动画双哈希更清楚，但会改变动作引用、重放及认证身份，当前不采用。若未来改变身份语义，必须单独版本化。

## 数据与生命周期

1. P7 adapter 收取原生结果，先区分是否收到回复及是否符合协议。稳定状态、末帧和完整动画分别处理。
2. 动画进入应用持有的动态区。按固定大小chunk验证、哈希和持久化，释放已处理的工作缓冲；没有人为总帧数、总cells、总字节或run动画quota。每块、每页和同时驻留缓冲有明确预算。
3. 动态区的内容身份绑定run/game/seed/action sequence。帧范围连续，颜色和尺寸有效，块hash可核对。chunk先写，完整manifest最后原子发布。大索引分段；不能为了描述无限增长数据又构造一个无限增长JSON清单。
4. 完整观察哈希按原规范字节流增量计算。元数据规范化、默认空字段、键排序、转义规则、数值规则、完整帧顺序均与既有 `score.canonical_bytes` 一致。chunk边界不影响sha256。
5. actor直接读取稳定状态、末帧、完整观察引用、动画页引用。禁止先生成受小消息上限约束的全量 `ObservationState` 再截断。观察引用继续绑定完整原身份，不能悄然换成末帧hash。
6. 历史、回放、重放和准备器消费迭代器与页。禁止读回全部动画再切片、deepcopy整个批次、拼成工具响应或网页JSON。P7预测继续针对稳定帧；需要中间动画时主动读取。
7. 当前动作处理完后释放临时对象。必须同时清除adapter `_current`、broker `_current.frame`、`_replay_observations`、replay witness等长期强引用，改持只读结果handle。完整结果校验、必要动画持久化和动作身份提交完成后才释放arena；SDK自己仍持有对象时不得宣称已经释放。保存的过关证据和失败研究所需动画持久化；已经被引用的块必须保留。没有耐久引用的暂存区在明确生命周期结束后清理，不能删除尚未收口/仍被回放引用的数据。

SDK目前先构造完整Python结果对象，落盘分块不能消除这个原生接收峰值。接收端动态区应尽量在SDK adapter/worker内建立，以小引用跨进程；原生库未提供增量结果时，明确保留这个边界，避免第二次完整复制。实际内存、磁盘、I/O、取消或deadline失败必须有明确状态；不能宣称动态区等于无限物理资源。

## 容量职责

| 通道 | 容量对象 | 处理方式 |
| --- | --- | --- |
| 原始动画动态区 | 当前chunk及并发工作缓冲 | 流式、无人工总长限制；实际资源失败显式报告 |
| 完整观察身份 | 规范token流 | 增量哈希，不受512KiB模型视图或262144 cells聚合限制 |
| 稳定状态视图 | 当前帧及有界元数据 | 保持结构校验和小消息预算；过大元数据分页并给完整引用 |
| actor上下文/工具结果 | 最终响应，含envelope/newline/编码 | 在构造最终消息前预算；分页/摘要有完整引用，异常不能吞掉 |
| IPython export/RPC | 运算输出和协议传输 | 原有限控制保留；动画通过引用专门处理，不靠调大通用RPC上限 |
| console/live events | 状态与帧页引用 | 小事件、分块帧；完整95帧等不能被64层parser静默拒绝 |
| prepared replay | manifest/索引页/帧页 | 保存时准备，分页读取；不以32MiB单level、8192总帧截断完整动画 |
| 证书来源完整性 | 来源字节流及封口证据 | 流式静态hash；动画文件不因通用64MiB来源读取预算被截断 |
| 失败经验来源 | 小研究摘要与动态动画引用 | 保留来源scope/hash校验；动画不进入32MiB单文件/64MiB经验正文累计预算 |
| 诊断 | 有界单条诊断和索引 | 合并重复诊断，保留首次/最新/次数；异常必须可检索 |

现有一般小消息限制保留其用途：研究context56KiB、feedback60KiB、研究响应1MiB、revision1MiB；Prime code16KiB、cell output64KiB、export256KiB；Pi compact raw line16MiB、retained event1MiB。完整动画不得被塞回这些通道。研究响应必须按最终wire bytes预算，消除1MiB payload与1MiB envelope接收之间的不一致。

## 动作结果与异常合同

| 阶段 | 发生错误后的状态 | 可执行行为 |
| --- | --- | --- |
| not-dispatched | 请求/预测/资源前置拒绝 | 修改请求，无动作发生 |
| dispatched-no-reply | 真正结果未知 | 停止该动作后缀，不重派；有界收口并记录基础设施中断 |
| reply-received-invalid | 收到回复但协议无效 | 协议错误；不把未验证状态当事实，不重派 |
| validated-not-durable | 游戏结果已知、证据未保存完整 | 明确结果已知但未提交，暂停；不授予新路线/分数/续跑权限 |
| durably-committed | 原始结果、动作及身份已提交 | 正常处理GAME_OVER/RESET、失配、下一步 |
| derived-failed | 原证据完整，本地视图/网页/摘要失败 | 只读重建派生物；不再调用SDK；重建失败明确暂停或展示失败 |

异常必须按这些阶段分类，移除“整个执行块任意Exception＝动作未知”。hash、存储、观察解析、history、模型视图和console投影的错误分别记录安全错误码及阶段。提交失败不能发布可用证书；完整raw结果也不能自动变成已验证通关。

永久阻塞不得反复让LLM尝试一个不存在的恢复API。未知结果或本地不可恢复失败一旦判定，给模型明确状态与允许的只读操作，有限收口并释放游戏槽；不计作普通推理失败。旧失败计数和未封口证据保持历史原样，诊断补充不能伪造旧成功。

## 明确警告

诊断字段：`diagnostic_id`、安全`code`、`severity`、`stage`、`action_sequence`、`outcome_known`、`durable`、`observed`、`limit`、`unit`、`recovery`、首次/最新出现及次数。对没有人为总限额的动态区，不编造limit；实际资源失败用独立错误码与实际可知信息。

- 写入结构化日志、运行诊断及最终summary；当前模型收到同一安全状态。
- 控制台游戏总览与运行状态显示持续的小警告标识，详细信息按需展开。复用既有状态区域；不能添加闪烁banner、撑开空白或在轮询时反复消失重现。
- 重复错误按diagnostic_id合并计数。恢复后保留已恢复记录，不删除告警历史。
- 提示明确：哪个环节、测量值/单位、相应限制、动作是否已执行、结果是否确定、证据是否完整、当前能继续还是暂停。
- 不公开原始异常内容、私有路径、凭据、provider payload、源码或模型思维链。详细私有异常可在operator拥有的证据中留存。
- 合法分页/摘要不是底层错误，标明完整内容已保存和可读引用；非预期数据拒绝、保存失败或缺展示记录不能只标普通加载中。

## 身份、兼容与部署

完整观察v1哈希语义不变。新增动态区与派生manifest是新文件格式，需要显式版本/校验；不能原地替换旧证据或旧prepared revision。现有sealed route、后续关卡和择优注册保留。

`solution_certificates._VERIFIERS`绑定broker/observation_state/replay/solutions等代码。源码变动后旧认证不会自动仍ready。必须显式支持已审核的精确冻结verifier profile及其静态来源检查，或产生有证据支持的新认证。禁止通配旧verifier、取消hash核对、用“哈希看起来相同”跳过既有保存时SDK见证、重新重放全部历史关卡来掩盖兼容设计缺失。兼容profile由应用/operator明确绑定，不从缓存猜权威。

真实两路guest保持各自原wheel和期限。新代码经过focused验证、复审、`make promotion-check`后只在自然关卡边界接入。打包资源及工具allowlist变化按仓库部署闭环处理；仍使用Prime已有注册机制。完整25题官方开卡不属于此修复授权。

## 验收

1. 既存BP两批57帧与G两批95帧纯数据fixture均成功接收、保存、完整哈希、稳定视图和全部动画分页；无需模型、API或SDK重放。
2. 旧范围内规范byte/hash逐项相同；改变chunk边界不改变完整hash；每帧顺序、元数据和帧数变化必须影响完整身份。
3. 大于64帧、64MiB来源、8192展示帧的惰性fixture走分块/分页，无相应聚合截断，不把所有块拼回内存。驻留缓冲检查控制chunk及页，原生SDK峰值单独列边界。
4. SDK明确返回GAME_OVER后本地派生失败不再误标unknown；真正丢回复仍不可重派。注入磁盘/哈希/校验/展示失败，分别验证状态、计数、诊断和无重派。
5. 所有公开诊断的secret/path/provider哨兵不可泄漏。警告在模型、summary、console同一身份下可见且重复更新不造成布局跳变。
6. 每个现有保存游戏/关卡的来源、动作、分数、稳定认知及最新回放保留；静态旧证书兼容读取禁止SDK构造，旧事实不可被UI修复改写。
7. 只以实际命令和运行证据标Verified。设计、单元fixture、动态区实现与真实新轮次通关分别记录，不能相互替代。
